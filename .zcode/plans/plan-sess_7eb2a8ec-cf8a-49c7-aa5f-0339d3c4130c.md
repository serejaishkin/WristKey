Авторизация Windows Logon для WristKey: доработка нативного V2-провайдера + DPAPI-хранение пароля

Текущее состояние (по исследованию): продакшн-путь — нативный C++ провайдер (`windows-credential-provider/`, CLSID `{7E1B7B8A-...}`), который при клике по плитке ходит по пайпу `\\.\pipe\wristkey` в демон и сериализует Kerberos-credential. Разорванные звенья: (1) демон после успешного BLE challenge возвращает строку `"authenticated"` вместо реального пароля; (2) пароль Windows негде хранить; (3) мелкий баг формата ответа в пайп-сервере; (4) часы могут не отвечать на challenge без недавнего движения запястья.

## Этап 1 — демон: хранение и выдача пароля

1. **Хранение пароля (DPAPI).** В `desktop/crates/core` у `PairedDevice` уже есть поле `windows_password: Option<Vec<u8>>` (core/src/lib.rs:158) и методы `set_device_password`/`get_device_password` (lib.rs:322-330), колонка в SQLite есть; в platform-win уже есть `WindowsKeyProtector` на `CryptProtectData/CryptUnprotectData` (platform-win/src/lib.rs:10-21).
   - Обеспечить, чтобы при записи пароль шифровался DPAPI (добавить шифрование на стороне записи — в daemon или Tauri-слое), а в БД лежал только шифротекст.
   - Добавить способ задать пароль: Tauri-команда (GUI) + действие `"set_password"` в протокол пайпа (для CLI/тестов). Пароль в открытом виде только в памяти процесса.

2. **Выдача пароля после challenge.** В `do_ble_unlock` (desktop/crates/daemon/src/lib.rs:284-302): после успешного `session.verify_unlock(...)` вместо `Ok("authenticated")` — расшифровать `windows_password` через DPAPI и вернуть его. Если пароль не задан — возвращать ошибку `"password not configured"` (провайдер покажет статус и не завершит вход).

3. **Багфикс пайпа** (lib.rs:271): ответ об ошибке пишет литеральный `\n` внутри raw-строки — заменить на корректный перевод строки.

## Этап 2 — провайдер V2 (минимальные правки)

Код сериализации уже соответствует Microsoft-сэмплу (`GetSerialization` → `RequestUnlockFromDaemon` → `PackUnlockCredential` c `KERB_INTERACTIVE_UNLOCK_LOGON`, Provider.cpp:432-596). Что сделать:
1. Проверить/поправить различение ошибок демона: показывать пользователю конкретный статус («пароль не настроен», «часы не подтвердили», «таймаут») вместо общего «подтвердите на часах».
2. Поддержать сценарий `CPUS_LOGON` полноценно (сейчас имя пользователя берётся из SetUserArray — убедиться, что плитка появляется и для входа, и для разблокировки).
3. Сборка: `cmake -S windows-credential-provider -B build -A x64`, регистрация `install.ps1` (System32 + regsvr32), как в README_V2.md.

## Этап 3 — часы (Wear OS): устранить таймаут challenge

`respondToPairedChallenge` (wear-os/.../WristKeyBleService.kt:299+) не подписывает challenge, если `motionDetector.hasRecentMotion() == false` — тогда десктоп ждёт 10 сек и отваливается. Добавить запасной путь подтверждения: если движения нет, отправить на часы локальное уведомление «Подтвердить разблокировку ПК» с кнопкой (или принять тап по экрану) и подписать после подтверждения; без подтверждения — явный отказ-ответ вместо молчания.

## Этап 4 — сквозная проверка

1. `cargo build` daemon + Tauri; задать пароль через GUI/команду.
2. Юнит: пайп-запрос `{"action":"unlock"}` без часов → внятная ошибка; с часами (после фикса Этапа 3) → возвращает реальный пароль, равный заданному.
3. Собрать и зарегистрировать DLL, выйти из системы, убедиться что плитка WristKey появилась; клик → часы подтверждают → вход выполняется.
4. Обновить AI_HANDOFF.md (снять пометку «НЕПОДТВЕРЖДЕНО» только после реальной проверки плитки).

Порядок: Этап 1 → 2 (это даёт рабочий вход при ручном подтверждении на часах), Этап 3 можно отдельно/параллельно. Ничего не удаляю; legacy C#-провайдеры не трогаю.
